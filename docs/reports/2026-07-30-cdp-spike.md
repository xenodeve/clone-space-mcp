## Q1 — Does `getEventListeners({depth: -1, pierce: true})` return the whole subtree in one call?

**YES**, for open shadow roots and same-origin iframes.

One call on `document.documentElement` returned **6 listeners**, including all **4** click
listeners the fixture declares:

| Where the listener lives | Declared | Returned |
|---|---|---|
| Light DOM (2 carousel buttons) | 2 | ✅ |
| Open shadow root (`shadow-card` → `.mark`) | 1 | ✅ |
| Same-origin iframe document (`frame.html` → `.dot`) | 1 | ✅ |
| **Total click** | **4** | **4** |

Also returned: 1 `scroll` and 1 `touchstart` — GSAP/ScrollTrigger's own handlers, which the
fixture does not declare but which the extractor will have to attribute rather than report as
page behaviour.

**What this does not cover.** Closed shadow roots (the fixture only has an open one).
Out-of-process iframes — this fixture's iframe is same-origin, so a same-target success here
says nothing about a cross-origin one, and an OOPIF is a separate CDP target that will need its
own session. Listeners added after the call; this is a point-in-time snapshot.

**Consequence for v1:** one call per target is enough, so the per-node round-trip the plan
wanted to avoid is genuinely avoidable. Budget for one session per OOPIF.

## Q2 — `DOMSnapshot.captureSnapshot` at ~3000 nodes: how many MB?

**1.381 MB at 6160 nodes**, with 40 computed properties requested.

| | Nodes | Bytes | MB | ms |
|---|---|---|---|---|
| Fixture as authored | 159 | 23,947 | 0.023 | 2.7 |
| Fixture + 3000 synthetic nodes | 6,160 | 1,447,751 | 1.381 | 76.9 |

Marginal cost: **237 bytes per node**. At the 3000 nodes the question actually asked about,
that is roughly **0.7 MB** — the snapshot was inflated past the target so the number would be
measured at scale rather than extrapolated from 159 nodes.

**Verdict: cheap. No property allowlist is needed in v1.** The columnar, string-interned
representation is doing its job; the 40-property list is not the cost driver it was assumed
to be.

**What this does not cover.** The synthetic nodes are uniform `<span>`s, so they intern far
better than a real page's variety of tag names and inline styles — treat 237 B/node as a floor.
`includePaintOrder` was off; turning it on adds a per-node integer. The timing is one sample,
so 76.9 ms is indicative, not a benchmark.

## Q3 — Does `CSS.getStyleSheetText` bypass CORS?

**YES.**

The premise was established first, because a "yes" means nothing if the sheet was readable
anyway: in-page, `document.styleSheets[n].cssRules` on the cross-origin sheet throws
**`SecurityError`**. Through CDP, the same sheet returned **593 bytes** of real text,
containing the fixture's marker string.

| | |
|---|---|
| Page can read `cssRules` | no — `SecurityError` |
| Stylesheets seen by CDP | 4 |
| Cross-origin sheet found by CDP | yes |
| Text returned | 593 bytes, contains the fixture marker |

**What this does not cover.** A sheet served with `Access-Control-Allow-Origin` (it would be
readable in-page anyway). Sheets injected by an extension or a service worker. `@import` chains
from a cross-origin sheet.

### The wrong answer this question gave first

The first run of this harness reported **NO**, with
`Protocol error (CSS.getStyleSheetText): No style sheet with given id found`.

That was a harness bug, not a finding. The harness collected `CSS.styleSheetAdded` events and
then reloaded the page; navigation invalidates `styleSheetId`s, so `find` returned an id from
before the reload that could no longer resolve. Removing the reload — `CSS.enable` already
replays `styleSheetAdded` for existing sheets — changed the answer to YES.

It is recorded here because the failure mode is the dangerous one: a bug in the measurement
produced a plausible negative that would have shaped a v1 interface around a capability that
exists. `scripts/spike-cdp.ts` carries a comment at that line so the reload does not come back.

## Unplanned finding — Playwright's client does not work under Bun

This was not one of the six spike questions. It surfaced while building the harness and it
matters more than any of them, because it contradicts a decision already taken: this repo is
Bun-only, and the pipeline's architecture rests on Playwright's `recordHar` and `routeFromHAR`.

Measured on this machine, same script, same Playwright, same Chromium:

| Layer | Bun 1.3.14 | Node 22.23.1 |
|---|---|---|
| Raw CDP over websocket, no Playwright client | **OK, 99 ms** | not run |
| `chromium.connectOverCDP` (Playwright client, websocket) | **timeout, 20 s** | not run |
| `chromium.launch` (Playwright client, `--remote-debugging-pipe`) | **timeout, 30 s** | **OK, 68 ms** |

Bun spawns Chromium successfully (the process starts and its stderr is readable), and Bun
speaks CDP over a websocket in 99 ms. Both Playwright transports still hang. So the fault is
**inside Playwright's client under Bun** — not the pipe transport, and not Bun's networking.
The first hypothesis was that `--remote-debugging-pipe` needs extra stdio descriptors Bun does
not wire up; the websocket probe falsified it.

**Current workaround, in place:** the spike runs under Node and starts the fixture server as a
Bun child process (`scripts/fixture-serve.ts`), which announces its origins on stdout. Each
half runs where it works, and nothing has been rewritten for a decision that has not been made.

**The decision this forces** is tracked separately — it is the developer's, not an
implementation detail:

1. **Node for browser-driving code, Bun for everything else.** Node 22 runs the repo's
   TypeScript directly, so the cost is a runtime boundary, not a rewrite. `Bun.serve` /
   `Bun.build` stay on the Bun side.
2. **Stay Bun-only and drop Playwright.** This means re-implementing `routeFromHAR`, which is
   the single mechanism the replay architecture depends on. High cost, high risk.
3. **Wait for an upstream fix.** Not actionable now.

**What this does not cover.** One machine (Windows 11, Bun 1.3.14, Playwright 1.62.0). Not
retested on a Bun canary, and no upstream issue was searched for or filed.
